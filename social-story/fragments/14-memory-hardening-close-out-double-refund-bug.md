## LinkedIn 1/2 — Narrative

*I found a bug in Safeeely that could've sent the same refund twice.*

It was July 1, 2026. I was deep in a self-review pass through the dispute-resolution code — the part of Safeeely where, if a deal goes wrong, an AI looks at the evidence from both sides and decides who gets paid.

I wasn't looking for this bug. I was looking for something else entirely (a memory leak, more on that below). But I found something worse.

There was a narrow timing window where the same dispute, retried at just the wrong moment, could trigger the *entire* resolution process a second time. A second refund. A second commission payout. A second trust badge awarded.

For one dispute.

Nobody had hit it yet. No user ever saw a duplicate refund. But the window existed, and eventually, at scale, it would have fired.

That's the part of building financial software that nobody talks about. It's not the shipped feature that keeps you up at night — it's the one-in-ten-thousand timing window sitting quietly in code that already works fine 99.99% of the time.

I closed it with a simple guard: once a dispute is resolved, it's locked. No re-runs, no matter how the retry lands.

Same day, same review pass, I also found a bug going the *other* direction — a case where Safeeely was silently failing to pay out a commission it owed, on certain AI-resolved milestone disputes. No crash. No error log. Just quietly wrong.

Two bugs, opposite directions, same root cause: money logic is unforgiving, and "it works in testing" is not the same as "it's correct."

Escrow only works if people can trust it completely. That trust doesn't get built in the feature you launch. It gets built in the pass you take through the code after it's already shipped, when nobody's watching and there's no demo to show for it.

## LinkedIn 2/2 — Insight/take

*The most valuable work I did on Safeeely this summer produced zero new features.*

On July 1, 2026, I spent the day not building anything new. I went back through code that was already live — already working, already shipped — and tried to break it on purpose.

I found six real issues. A background browser process that, if it ever crashed, would permanently jam every future receipt behind it. A broadcast function quietly holding an entire user list in memory for the full duration of a mass send. And the big one: a timing window where a single dispute could get resolved, and paid out, twice.

None of these were things a user reported. None of them showed up in a demo. If I'd spent that day building a new feature instead, I'd have something shinier to post about.

Here's the take: in any product that touches real money, the review pass is the feature. Shipping fast gets you users. Going back and finding the bugs that only show up under concurrency, under retries, under scale — that's what lets those users trust you with their next transaction, and the one after that.

Most startup content glorifies the launch. Almost none of it glorifies the Tuesday where you sat alone rereading your own code looking for the ways it could quietly hurt someone.

That Tuesday is where the trust actually gets built. I'd take more of those days over more feature launches, every time — especially this early, especially with real money moving through the system.
